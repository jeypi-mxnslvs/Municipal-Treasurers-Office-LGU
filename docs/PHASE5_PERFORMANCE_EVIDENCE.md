# Phase 5 scalability evidence — 2026-09-21

Scope: local disposable Supabase PostgreSQL 17 fixtures. No remote municipal data was written. The linked migration list shows `20261006_phase5_bounded_reads.sql` and `20261007_phase5_notice_candidates.sql` applied.

## Reproducible fixture and checks

- Created minimal `properties` and `delinquency_period_verifications` tables in an ephemeral database; applied the existing `20261006` migration locally. Inserted 25,000 synthetic active properties across 33 barangays, with one owner `O'Neil % _ 雪`, then ran `ANALYZE`. Enabled RLS with an authenticated-role read policy. Applied `20261007` **locally only**.
- Under `SET ROLE authenticated`, `list_properties_page(1,25)` and `(2,25)` returned 25 rows each, a count of 25,000, and zero overlapping IDs. The first page JSONB was 7,552 bytes; a 100-row page was 29,952 bytes (minimal fixture schema).
- Literal search for `O'Neil % _ 雪`, `%`, `_`, and a backslash-containing name returned one row each; trimmed empty input returned 25,000 total but still only the requested page.
- `dashboard_property_counts()` returned 25,000 properties, zero shell records, and 33 barangay buckets. Exact TD lookup returned one match.
- Batch notice navigation requests 25 candidates at a time. Each displayed notice separately loads that parcel's approved assessment and verification evidence, and refuses to render when either read fails, the schedule is unavailable, or the parcel is a shell record; no full-roll client load is needed.
- Import preflight reuses exact-TD lookup in chunks of 500, avoiding an unbounded `in(...)` URL and PostgREST's default row limit. This does not constitute a 25,000-row atomic import throughput test.
- `EXPLAIN (ANALYZE, BUFFERS)` execution times in this disposable container: page 1 **106.8 ms**, page 1000 **71.4 ms**, quoted/Unicode search **209.9 ms**, dashboard counts **40.4 ms**, targeted owner/barangay search **12.6 ms**. Last-page notice candidate scan with its partial index: **24.7 ms**. These are database timings, not HTTP latency or browser heap measurements.
- Subsequent disposable fixture: same 25,000 parcels across 33 barangays but with all active property columns, five historical valuation objects per parcel, longer addresses, and 100,000 verification rows. Property table and indexes occupied **53 MB**. With RLS enabled under `authenticated`, page 1 returned **25 rows / 41,270 UTF-8 bytes** and page size 100 returned **165,044 UTF-8 bytes**; pages 1 and 2 were disjoint. Quoted/Unicode, literal `%`, and literal `_` searches each found the intended single record.
- Wider-fixture database timings: page 1 **138.7 ms**, page 1000 **166.7 ms**, quoted/Unicode search **23.0 ms**, dashboard counts **44.6 ms**, and last-page notice candidate scan **17.1 ms**. Four concurrent authenticated-role page requests completed in **156.7–326.9 ms** database execution time (pages 1, 2, 500, 1000); process orchestration took **761 ms** wall time. The deep page spilled approximately **28 MB** to PostgreSQL temporary storage during sorting; this warrants review with representative production data.
- Production build after splitting the installed Supabase dependency into its own chunk: main JS **475.27 kB / 147.13 kB gzip**, Supabase **220.34 kB / 58.07 kB gzip**, deferred XLSX **332.97 kB / 114.68 kB gzip**. The 500 kB Vite chunk warning is resolved without suppressing the threshold. Previous unsplit main JS was 831.74 kB / 237.02 kB gzip.

## Limits and review gate

Both fixtures use fabricated records, not sanitized real parcels or the deployed HTTP stack. The wider fixture includes historical JSON and four verification rows per parcel, but not the full range of real valuation and schedule shapes. Four database sessions are not a concurrent browser test. No agreed HTTP response-time or browser-memory limit has been provided. This is **not** production-volume certification. Exact monetary delinquency and clearance KPIs remain unavailable: their authoritative TypeScript projection depends on per-period verification and approved schedules, and a SQL approximation would violate the SSOT. Dashboard property/shell counts are SQL aggregates; they must not be read as monetary totals. Property pages and dashboard counts are invalidated selectively; financial assessments and computation schedules are deliberately fetched fresh rather than cached across assessor actions.

Before Phase 6, the human performance reviewer should exercise representative full-size property and verification data through authenticated HTTP/browser sessions, establish and evaluate response/memory thresholds, assess the observed deep-page sort spill, and explicitly accept or reject the unavailable monetary KPIs. No production data load or migration push was performed by the agent.
